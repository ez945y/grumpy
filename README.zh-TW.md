# grumpy

[English](README.md) · **繁體中文**

一個在讓你寫入之前會先跟你爭辯的知識庫。

兩個檔案。零依賴。沒有伺服器、沒有 embedding、沒有向量資料庫。只需要
Python 3.11+ 和標準函式庫。

## 為什麼它會拒絕你

多數 agent 記憶工具都在優化「捕捉」：讓你更容易存東西進去，混亂之後再說。
但那個混亂才是真正的問題。一個月之後你有同一件事的四個版本，沒有一個標了
日期，也沒辦法判斷哪個還算數。載入它的成本已經超過答案本身的價值。

grumpy 選擇拒絕。每一次寫入都要過三道關卡：

| 關卡 | 限制 | 理由 |
|------|------|------|
| 未知標籤 | 必須已經在標籤樹裡 | 一個無限成長的詞彙表就不再是詞彙表 |
| 內文長度 | 2000 字元 | 更長的筆記裝了兩個主張，而第二個會變得搜不到 |
| 與現有筆記重疊 | 60% | 同一件事的兩份副本會各自漂移，然後沒人知道哪份是對的 |

每次拒絕都會告訴你它找到了什麼、為什麼擋下來，讓你可以改成擴充既有的筆記。
真的確定要寫的話，`-f` 可以一次繞過這三道。

這就是整個賣點。其餘的設計都是從「讓回想保持便宜」推導出來的。

## 它想解決的問題

大型系統散落在多個 repository 裡。Agent 有能力全部讀完，而那正是問題所在，
因為它每一次工作階段都會再讀一遍。同一個下午的挖掘不斷重演：這件事歸哪個
repo 管、為什麼乾淨 checkout 之後建置會失敗、當初對這件事做了什麼決定又是
為什麼。學到的東西沒有一樣活過它被學到的那個 context。

不斷成長的 memory 檔解決不了這件事，README 也一樣，因為兩者都逼你做同一個
取捨：全部載入，或者什麼都找不到。

我們要的東西比較接近「回想」而不是「閱讀」。此刻真正相關的那一件事，其餘
一概不要。我們的細胞持續在汰換，而我們從來不會察覺這件事正在發生；延續下來
的不是物質，是模式。Agent 的 context 也是這樣換代的。這個工具試圖成為那個
活過 context 的模式，讓一個 agent 能交接給下一個，而兩者都不必重新推導已經
被知道的事。

## 對 context 輕量，是刻意設計的

- **原子化筆記。** 搜尋命中應該**就是**答案，不是一份還要略讀的文件。
- **大東西是另一個類別。** 地圖或表格屬於 `reference`，放在 `docs/`，一次讀
  一個段落。搜尋只顯示它的摘要和段落名稱，永遠不顯示內文，所以看一份大綱只
  花幾行，你只把需要的那一段拉進來。
- **連結是雙向的。** 筆記會引用它依賴的東西；而落在被引用那一則的人，需要
  找得到引用者。一個命中會通往整個主題，不會走進死路。
- **已了結的會消失。** 修好的缺陷是歷史，而歷史會擠掉還在咬人的東西。搜尋會
  告訴你它藏了幾筆。
- **標籤是一棵樹，用 slug 引用。** 把一個標籤換到別的分支只是改一行，不會
  動到任何一則筆記。

## 開始

```bash
git clone <this repo> grumpy
./grumpy/grumpy.py init ~/my-project-notes --name my-project-notes \
    --title "My project notes"
```

這會複製引擎、寫出一份帶有自己筆記 id 前綴的實例設定、一棵起始標籤樹，以及
一份給會載入 skill 的 agent runtime 用的 `SKILL.md`。接著改兩個地方：
`tags.md` 的 `area` 分支，還有 `SKILL.md` 裡的 `description`，後者決定這個
skill 到底會不會被觸發。

## 使用

```bash
./grumpy.py search <query> [--tag T] [--kind K] [--repo R] [--all] [--expand [HOPS]]
./grumpy.py issues [--severity S] [--repo R]      # 未解決的缺陷，最嚴重的在前
./grumpy.py read <id> [--context] [--section NAME] [--full]
./grumpy.py add --title T --kind K [--tags a,b] [--repos x,y] [--stdin]
./grumpy.py tags [--add SLUG --parent P] [--move SLUG --parent P]
./grumpy.py discuss <id> -m "..."
./grumpy.py init <dir>
```

處理缺陷時該優先用的是 `read --context`。它會給你那則筆記，加上所有連到它的
東西，並依類別列出。單看一個缺陷會留下幾個明顯沒答案的問題（有沒有因它做過
決策、有沒有人認領、哪份 runbook 繞得過去），而要開五個檔案才能回答的話，
實際上沒有人會去開。

六個類別：`architecture`、`known-issue`、`decision`、`runbook`、`reference`、
`task`。選擇的判準是：**如果換一個人來做同一件事，這則筆記還會一樣嗎？**
一定一樣，代表系統本來就是那樣。可能不一樣，代表有人做了選擇，那麼這則筆記
就必須寫得出它否決了哪些替代方案。

搜尋是雙語的。FTS5 負責英文，含詞幹還原與排序；而由於它的分詞器會把一整串
沒有空格的中日韓文字當成單一 token，FTS 回答不了的查詢會退回子字串掃描。

筆記是 markdown 加一小塊 frontmatter。所有東西都能用 `cat` 讀、用任何編輯器
改。CLI 只是方便，從來不是必要。

## 檔案結構

```
grumpy.py        引擎，對任何特定專案一無所知
test_grumpy.py   107 個測試
grumpy.conf      實例設定：筆記 id 前綴、名稱、標題
tags.md          標籤樹，以及它強制的那些慣例
SKILL.md         給 agent runtime 的入口
notes/           原子化筆記
docs/            參考文件
```

兩個引擎檔案不帶任何專案資訊，這正是一份副本可以服務任意多個知識庫的原因。
實例裡的其他東西全部都是內容。

## 值得留下的筆記

失敗模式不是筆記太少，而是**沒有人敢相信的筆記**。

**寫下你查證過什麼**：`file.go:123`，或者你跑過的指令和它的輸出。一個沒人能
重新驗證的主張會被盲目相信，然後在某一天被發現是錯的。

**區分觀察到的和推論的。**「我在原始碼裡讀到」和「我跑過而且看到」是不同的
信心水準，所以要寫清楚是哪一種。一則自信但錯誤的筆記比沒有筆記更糟，因為
下一個讀的人不會再去查證。

凡是 `git log` 或看一眼檔案就能知道的，一律略過。價值完全在於那些花了時間
才弄清楚的事。

## 測試

```bash
python3 -m unittest test_grumpy -v
```

單元測試涵蓋 frontmatter 解析、標籤樹、連結圖與它的走訪、段落切分、近似重複
偵測，以及索引時效。端對端測試把 CLI 當成 subprocess 來驅動。最後一組驗證
放在它旁邊的實際內容：每個標籤都解析得到、每個 wiki 連結都指向真的存在的
東西、id 唯一且與檔名相符、沒有任何入口文件引用已被刪除的筆記。這一組在
空引擎或剛生成的實例上會乾淨地跳過，所以兩者開箱都是綠的。

手動編輯筆記之後記得跑一次。
