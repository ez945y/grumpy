## 引擎放在哪

`init` 建出來的知識庫只裝知識 —— `notes/`、`docs/`、`tags.md`、`grumpy.conf`、
`SKILL.md` —— 引擎留在你 clone 的地方，放在知識庫旁邊，而不是裡面：

```
~/work/
  grumpy/          <- 這個 repo，clone 一次
  team-kb/         <- 只有知識
  other-kb/
```

一份 clone 就能服務這台機器上所有的知識庫；要分享給別人的知識庫帶的是知識，
而不是一份被複製進去的工具；知識庫的 git 歷史也不會被引擎的 diff 塞滿。

你想把 `grumpy.py` 複製進知識庫、讓它自成一體也可以，兩種擺法都支援。

## 指令會對哪一個知識庫動作

由最明確的開始：

| | |
|---|---|
| `--root PATH` | 蓋過其他所有的 |
| `$GRUMPY_ROOT` | 預設值 |
| 當下的工作目錄 | 前提是裡面有 `grumpy.conf` |
| 引擎自己所在的目錄 | 你把引擎複製進去的那種自成一體的知識庫 |

```bash
cd ~/work/team-kb && ../grumpy/grumpy.py search "the thing"
~/work/grumpy/grumpy.py --root ~/work/team-kb issues
```

## 裝進 skills 目錄

`./grumpy.py install` 會把一個現成的知識庫連進 `~/.claude/skills/`，Claude Code
和其他會讀 skills 的工具就找得到它。加 `--project` 則是連到程式碼旁邊的
`./.claude/skills/`。之後要重開 agent 工具 —— skill 清單只在啟動時讀一次。

知識庫裡 `SKILL.md` 開頭的那段描述，是唯一決定 agent 會不會想到要用這個知識庫的
東西，寫得太模糊它就永遠不會被用到。`tags.md` 也值得看一下，那是筆記可以歸到哪些
領域的清單，不在上面的標籤 grumpy 會拒絕。

## 六個類別

每則筆記都屬於其中之一：

| 類別 | 裝什麼 |
|---|---|
| `architecture` | 東西是怎麼組起來的 |
| `known-issue` | 壞掉的東西 |
| `decision` | 一個選擇，和它的理由 |
| `runbook` | 有效的操作步驟 |
| `reference` | 地圖或表格 |
| `task` | 待辦的工作 |

前三個之間怎麼選，可以問：換另一個人做同樣的事，會不會寫出一樣的筆記？
一定一樣，代表系統本來就長那樣，那是 architecture。可能不一樣，代表有人做了
判斷，那是 decision，而且必須寫出其他選項是什麼。

## 硬要寫進去

每一道閘門都吃 `-f`。用它的時機是：你看過 grumpy 找到的東西，而它判斷錯了 ——
例如兩則其實無關、只是用詞剛好很像的筆記。強行跳過重複檢查之後，記得把另一則的
id 填進這則的 `links:`，讓它們還是連在一起。

## 連結筆記

`link` 是對已經存在的筆記補連結：

```bash
./grumpy.py link n-0004 n-0009 n-0011
```

要描述的東西有好幾個部分時就用它。先寫總覽、把它有哪幾條列出來，再一條一條寫、
寫完就接上去。`add --links` 表達不了這個順序 —— id 是建立當下才配發的，所以一則
筆記只能引用比它早存在的東西 —— 而這個順序正是值得鼓勵的那個，因為沒有被命名的
那條，就是最後被漏掉的那條。

## status，以及不要手改 frontmatter

```bash
./grumpy.py status n-0004 resolved
```

對 `status:` 跑 `sed` 會讓搜尋索引停在舊狀態，直到有人想起來要 reindex，而搜尋
正是這些檔案存在的理由。真的手改了，就用 `reindex` 強制重建。

## 什麼樣的筆記值得留下

問題從來不是筆記太少，而是沒有人相信的筆記。

寫下你實際查證過的東西，並且註明是讀到的還是跑過的，那是不同程度的把握。
凡是翻一下版本紀錄就會知道的，略過。

## 搜尋

直接對筆記檔跑 SQLite FTS5，檔案有變動就自動重建。分詞器切不開的查詢（中文就是
其中一種）會退回子字串比對。

## 架構

<img src="architecture.svg" alt="grumpy 架構：寫入時把關、檔案是唯一真相、索引是衍生的" width="680">

最上面那道閘門是它跟別的東西不一樣的地方，其他都從那裡長出來：一則筆記就是一個
檔案，所以多個人和 agent 可以同時寫、由 git 來合併；檔案是唯一的真相，所以索引
隨時可以丟掉重建；而修正是黏在被修正的那則旁邊，不是覆蓋它。

## 測試

```bash
python3 -m unittest test_grumpy -v      # 150 個測試
```

單元測試涵蓋解析、標籤樹、連結圖和重複檢查。端對端測試直接執行指令本身。最後一組
檢查放在旁邊的內容：每個標籤都解析得到、每個連結都指向真的存在的筆記、id 唯一。
沒有內容時那一組會跳過，所以剛 clone 下來就是綠的。
